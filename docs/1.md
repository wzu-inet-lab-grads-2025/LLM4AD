**研究方向判断**

你的项目本质上不是简单的“LLM 生成优化启发式”，而是在做：

> 面向 LLM4AHD/LLM4Opt 的闭环后训练式算法发现系统：EoH population search 产生候选算法，执行反馈转成 reward，再用在线 GRPO/LoRA 改变模型策略，同时由自适应 operator scheduler 和 collapse/recovery 机制维持搜索稳定性。

所以真正的研究目标我会拆成四个：

1. 让 LLM-based heuristic discovery 从一次性 prompting/evolution，变成可自我改进的 post-training loop。
2. 在高度耦合系统里稳定控制三件事：population 状态、LLM policy 漂移、operator 分布。
3. 用 BQR、gated deployment、anchor/deployed/latest LoRA 分离，避免 RL 奖励污染和策略坍缩。
4. 在 TSP/CVRP/OBP/JSSP 等任务上证明 sample efficiency、稳定性和跨规模泛化。

这条线是有 AAAI 级别潜力的。创新点如果凝练得好，不是“把 GRPO 接到 EoH 上”，而是“面向算法发现的稳定闭环后训练机制”。尤其是 [BQR reward](./llm4ad/tools/rl/rewards.py:99)、[gated LoRA deployment](./llm4ad/tools/rl/backends/trl_grpo_backend.py:417)、[自适应 operator scheduler](./llm4ad/tools/rl/operator_scheduler.py:121)、[collapse/recovery](./llm4ad/method/eoh_rl/eoh_rl.py:2248) 这几块，可以形成一套比较完整的方法论。

但以当前状态，直接冲 AAAI2027 还不够稳。主要问题不是方向低，而是证据链还散：旧实验主要集中在 OBP，当前实现已经和旧实验设计有明显偏移；机制很多，但还缺清晰 ablation 去证明每个机制为什么必要。AAAI 需要看到“不是工程堆叠，而是一个可解释、可复现、跨任务有效的闭环学习框架”。

**我对创新性的判断**

足够有潜力，但需要重新收束成一个明确贡献：

- 弱表述：EoH + GRPO + adaptive weight + collapse。这个像系统拼装，风险较高。
- 强表述：Algorithm Discovery with Stabilized Online Post-training under Coupled Population-Policy Dynamics。这个更像论文贡献。
- 最关键的 claim 应该是：普通在线 RL 会导致 code-style drift、reward hacking、population collapse；你的方法用 bounded relative reward、policy gating、anchor recovery、operator credit separation 来稳定闭环算法发现。

最严重的设计-实现不一致在 collapse stability 方案。你的文档明确写了要有冻结的 `bootstrap_seed_bank`，只在初始化阶段生成，用作 simple core/recovery 的稳定锚点，见 [adaptive_collapse_stability_plan_20260616.md](./docs/adaptive_collapse_stability_plan_20260616.md:1)。

但当前代码实际是动态 `_simple_pool`：初始化候选会进 pool，后续 evolved candidate 也会继续进入 pool，例如 [eoh_rl.py:1501](./llm4ad/method/eoh_rl/eoh_rl.py:1501)。这会让“simple core”被后期搜索轨迹污染，和“固定 seed bank 防漂移”的原设计不一致。

第二个明显问题是 simple pool 的筛选逻辑。当前 `_rebuild_simple_pool` 使用 `max(capacity, ceil(len/2))`，见 [eoh_rl.py:2191](./llm4ad/method/eoh_rl/eoh_rl.py:2191)。这意味着当 pool 数量小于 `2 * capacity` 时，几乎会考虑整个 pool，简单但性能较差的候选可能压过“性能前半部分再按复杂度选”的设计目标。

第三，文档里的 `recovery_parent_bank` 思路在实现里没有真正独立存在。恢复阶段主要仍从当前 active population 选 parent，而不是从 collapse 前保留的高质量、低复杂度候选银行中选。这会削弱 recovery 的多样性和稳定性。

**其他高风险点**

`adaptive_operator` 的实现已经从旧文档的 reward-EMA credit 变成了 count-based signal：frontier、parent、failure、fidelity 计数，见 [operator_scheduler.py:280](./llm4ad/tools/rl/operator_scheduler.py:280)。这未必错，但意味着旧实验报告不能直接证明当前 scheduler 版本有效。

当前 `Population` 会截断到 `pop_size`，见 [population.py:208](./llm4ad/method/eoh_rl/population.py:208)。而旧分析文档里有 population 增长到 100+ 的现象。因此旧实验和当前实现不是同一个系统，需要重新跑关键实验。

gated deployment 很保守：只有当训练后的 LoRA 产生 global improvement 且 fidelity 足够时才 accept，见 [trl_grpo_backend.py:417](./llm4ad/tools/rl/backends/trl_grpo_backend.py:417)。这有利于稳定，但也可能导致大量 GRPO update 被拒绝，实际性能提升主要来自 population search，而不是 post-training。论文里必须记录 accept rate，否则 RL 贡献会被质疑。

还有一个概念风险：配置里默认 `skip_sft: true`、`cold_start_from_base: true`，见 [eoh_rl.example.yaml](./configs/eoh_rl.example.yaml:1)。如果没有加载真实 SFT LoRA，那么所谓 anchor policy 不是“SFT prior”，更像 base/current startup state。这会影响你关于“回到 SFT 结构先验”的叙述。

**先说结论**

你直觉是对的：要证明“EoH-centered control 更稳定”很难，而且如果把 claim 写成“最终性能一定更好”，大概率会被证伪。更合理的 claim 应该降级为：

> 在同等 AHD 后训练框架下，search-governed policy adaptation 能降低有害策略更新、collapse 后恢复失败、operator feedback 失控和跨 seed 方差，同时保持或提升最终性能。

这不是纯 SOTA claim，而是稳定性 claim。它能不能冲 AAAI，取决于你能不能把“稳定性”实验做得非常扎实。

**怎么证明**

不要证明“架构哲学”。证明 4 个可测假设：

| 假设 | 对比组 | 指标 |
|---|---|---|
| gated deployment 有用 | always-deploy LoRA vs gated LoRA vs no-RL | harmful update rate、accepted LoRA rate、invalid rate、final gap 均值/方差 |
| recovery 比 CALM collapse 稳 | CALM best+seed reset vs yours best+simple_core+anchor/recovery scheduler | post-collapse k-step improvement rate、refill time、复杂度增长、恢复失败率 |
| BQR 比 CALM reward 更抗 reward hacking | CALM reward vs BQR vs binary improvement reward | exact-copy/random/leak/invalid rate、parent-improvement rate、frontier-improvement rate |
| adaptive operator 不是噪声放大器 | fixed CALM weights vs state weights vs yours normal/recovery scheduler | operator entropy、max-prob、operator credit calibration、最终方差 |

最难的是证明 “EoH-centered vs RL-centered”。这需要同一套代码里做两个 mode，否则差异会被实现细节污染：

1. `RL-centered`: 模拟 CALM，GRPO trainer 主导 generation/reward/pool side effects。
2. `Search-centered`: EoH controller 主导 prompt construction/population/collapse，GRPO 只是 backend。
3. 其他都保持一致：同模型、同 reward、同 operators、同 collapse、同 budget、同 seed。

如果这个对比不显著，不能强行写成主创新。它可以作为系统设计选择，而不是论文核心 claim。

**证伪风险**

我认为最容易被证伪的是：

> EoH-centered control 比 CALM 最终性能更好。

因为 CALM 已经很强，而且它的开源实现也不是粗糙 baseline。更稳妥的是证明：

> 在性能接近或更好的情况下，显著降低 tail-risk：坏 seed、collapse 后不恢复、LoRA 更新污染、代码复杂度爆炸。

如果最终 gap 没赢，但稳定性大幅提升，论文仍有空间；但必须把问题定义成 “stable online post-training for AHD”，而不是 “new SOTA AHD”。

**你现在还剩哪些创新点**

不能再 claim 的：GRPO + AHD、co-evolution、collapse、parent-relative reward、injection/replacement/crossover 这些 CALM 已经覆盖很大一部分，见 [CALM](https://arxiv.org/abs/2505.12285) 和 [CALM repo](https://github.com/whxru/CALM)。

还能保留的：

1. **Search-governed policy adaptation**
   EoH controller 拥有 population/collapse/operator 状态，RL 是受控 backend。这个是架构差异，但单独不够强。

2. **Gated LoRA deployment + rollback**
   这是你最像“新东西”的部分：训练不等于部署，部署必须通过搜索收益和 fidelity gate。

3. **Policy-population coupled recovery**
   collapse 不只是 pool reset，还联动 anchor policy、simple core、recovery operator distribution。这个如果实现干净，可以成为核心创新。

4. **BQR / bounded relative reward**
   如果实验证明比 CALM reward 更少 reward hacking、更稳定，这是强点。

5. **normal/recovery 分离的 operator adaptation**
   这个是辅助创新。它需要证明不是噪声放大器。

我不建议再堆很多新机制。更需要的是把这几个点合成一个统一方法：**Stability-Aware Online Post-training for AHD**。

**是否需要额外补创新点**

需要补的不是“新模块”，而是“新问题定义 + 证明框架”。

可以补一个清晰概念：

> Behavioral Trust Region for AHD Post-training

也就是 policy update 不是按 loss 接受，而是按搜索行为接受：必须带来 frontier improvement、保持 executable fidelity、不能造成复杂度/invalid 爆炸。这样 gated deployment、BQR、anchor recovery 都能统一起来。

这比再加一个 agent、memory、reflection 更像 AAAI 论文。

**是否该重构项目**

我建议：**重构，但不要完全从零造平台。**

当前代码太脏会有一个严重后果：实验失败时你无法判断是方法不行、实现偏差、配置污染，还是历史遗留 bug。对于现在这种高度耦合系统，这是致命的。

推荐路线是 hybrid：

- 保留 LLM4AD 作为 **baseline/task adapter 平台**。
- 新建一个干净的 research core，不直接塞在 LLM4AD 深层逻辑里。
- core 只定义少数接口：`ProblemAdapter`、`PopulationStore`、`PromptOperator`、`RewardEngine`、`PolicyTrainer`、`DeploymentGate`、`CollapseController`、`ExperimentRunner`。
- LLM4AD、CALM、EoH、ReEvo 等都通过 adapter 接入。
- 当前代码作为 prototype，不再继续在上面叠复杂逻辑。

也就是说，不要“全部自己造 AHD 平台”，但要“自己造论文方法核心”。LLM4AD 适合做比较和扩展，不适合承载你现在这个干净证明链。

我的建议很明确：先写一页 method spec 和实验矩阵，再重构最小可跑版本。别先重构成大工程。先让 OBP/TSP 两个任务上能复现实验矩阵，再扩到 CVRP/JSSP。这样你会很快知道：这是一个 AAAI 方向，还是一个被 CALM 吃掉创新空间的工程变体。
